## 2. 协议做了什么

Shadowsocks 是一个**加密的 TCP/UDP 转发协议**：客户端把目标地址和数据加密后交给服务端，服务端解密后代为连接目标。

- **AEAD**（带关联数据的认证加密）是当前官方推荐的加密族。相对早期的流加密，它同时提供机密性与完整性校验，能拒绝被篡改的密文。选型时以官方 AEAD 文档列出的算法为准，不要沿用文章里的老配置。
- **Shadowsocks 2022（SIP022）** 是更新的规范，密钥格式与握手都与旧版不同。**服务端与客户端必须同代**，否则连不上——这类失败常被误判成「被墙了」。
- 协议本身**不做**：身份认证之外的访问控制、流量整形、出口地址选择、DNS 策略。这些都由客户端或链路上的其他组件决定。

## 3. 它能保证什么，不能保证什么

| 能 | 不能 |
|---|---|
| 客户端与服务端之间的内容被加密，中间人读不到明文 | 不保证「无法被识别为代理流量」 |
| AEAD 下密文被篡改会被检测到 | 不保证目标网站看到的出口地址是「干净」的 |
| 目标地址在第一跳之前不以明文出现 | 不保证 DNS 不泄漏——取决于客户端怎么解析（见第 4 节） |
| 服务端替你发起到目标的连接 | 不保证最终出口与第一跳是同一个地址 |

**不能由「用了 Shadowsocks」推出的结论**（这几条在上一版里被越界地写成了承诺）：

- 「IP 是干净的」——IP 信誉由各目标服务自行判定，动态变化，你无法核验。
- 「账号会被信任」——风控是多因子模型，出口地址只是其中一项。
- 「访问能力会恢复」——是否恢复由对方决定，换链路可能无效，也可能触发新的判定。

## 4. 第一跳与最终出口

```text
应用 → 本地 loopback 监听端口 → [第一跳：Shadowsocks 服务端] → …中转… → [最终出口] → 目标
```

- **第一跳**：你的客户端直接连的那台服务器，由你的配置决定，可确知。
- **最终出口**：目标看到的来源地址，由链路末端决定。若服务端背后还有中转或再出站，**两者不是一回事**，而且可能随时间变化。
- 所谓「固定 ISP 出口」只描述**最终出口的稳定性**，既不说明它的历史记录，也不说明任何一家目标服务怎么给它分类。

**DNS 的位置**：如果客户端用 `socks5`（不带 h），域名在本机解析，解析请求会走本机 DNS，域名因此暴露在本地链路上；用 `socks5h` 则把域名交给代理端解析。这是**应用级**的选择，不需要、也不应该为此去改系统 DNS 设置。

## 5. 本地客户端的用法边界

与 `RECOMMENDATIONS.md` 第 1 节一致，这里只重复三条硬约束：

1. 客户端**只在 `127.0.0.1` 上监听**，不要监听 `0.0.0.0`；否则同网段的其他机器可以直接借道你的出口。
2. **不修改系统代理**、不动 DNS、不启用 TUN / 虚拟网卡、不改路由与防火墙。需要出网的应用自己显式指向那个本地端口。
3. 停用时把应用侧的设置精确恢复；恢复不了就停掉该应用的出网路径并报告，**不要让它回落到直连**。

## 6. 配置模板（占位符，勿填真实值）

下面只示意结构。**真实的服务器地址、端口、密钥字段一律不写进任何交付文件**；`password`、`TunnelSecret` 这类字段在交付前必须替换成占位符，并用 `tools/redact_scan.py` 复查。

```text
# 结构示意，不是可直接运行的配置
proxies:
  - name      <本地备注名>
    type      ss
    server    <服务器地址>
    port      <端口>
    cipher    <按官方 AEAD 文档选择>
    password  <此处留占位符，不要填真实值>

listeners:
  - type      mixed
    listen    127.0.0.1
    port      <本地端口>
```

出包前自查：

```text
py -3 tools/redact_scan.py --dir <要外发的目录>
```

退出码 `0` 只代表「未命中已知模式」，**不代表安全**；退出码 `3` 表示存在扫描器解析不了的内容，这份报告本身不可信，必须人工看过。
