# 0012 按积压自动分配 Agent（提议）

- 状态：已实施（2026-10-01，feat/allocator-preview-20261001），默认「预演」。上限按下文建议值：每圈 5 单、每人 1 单、同一名额最多换人 2 次
- 来源：体验反馈 fb-2c3e8c868c（派任务的 auto mode）、fb-aded5a13c6（有活就塞给 builder，不要建单干等）、fb-8a7c79854b（Agent 利用率）

## 现在是怎么分配的（2026-10-01 核实）

| 环节 | 谁来分 | 自动吗 | 上限 |
|---|---|---|---|
| 网页指令（转任务、拍板、派发） | Leader 从指令队列领 | 多位 Leader 并行领，每条只给一位（`.claim.mutex`） | 每次 wait 领 1 条 |
| 讨论 / 独立作答 | 派发时人或 Leader 点名 | 否 | 点几个是几个 |
| 施工（build） | 派发时点名 builder | 否；builder 掉线只会「等」 | — |
| 审查（review） | `pick_reviewers` 从 reviewer 组里挑在线的 | **是**，排除作者、优先别的模型组 | 每单 n 个 |
| 顶替 | 守护 `auto_reassign`：过期 / 离线排队的名额换给同组在线的 | 是，但**跳过 build 和 review** | 每个名额最多改派 2 次 |

所以「按积压多少动态调人」**目前没有**：没有任何一处会看「待分诊 / 待施工 / 待审查各积了多少、谁闲着」然后把闲人派过去。实测当时 8 个 Agent 在线全部 idle，同时 126 个开放任务、31 条 Leader 指令卡着——其中大部分是孤儿领取（已由 fix/build-lifecycle 与 feat/multi-leader-visible 修掉），剩下的是「点名给了离线的人，在线的人没有被派」。

## 提议

守护每个周期跑一次**分配器**，只做一件事：把闲着的 Agent 派到最缺人的那一段。

1. **三段积压**：待施工（施工单的成员全部离线、或建单后超过 N 分钟没人领）、待审查（审查任务的 reviewer 离线或过期）、待作答（discuss / independent 的名额离线）。Leader 指令不在这里——那只能由 Leader 领，多位 Leader 并行已经解决。
2. **谁能接哪段**：沿用 `console/roles.json` 的 `builder_groups` / `reviewer_groups`；作者不审自己的单（已有规则）。
3. **派给谁**：在线且 idle、收件箱没有待领任务的 Agent；按「该段积压 ÷ 该段可用人数」从高到低填，最老的单先派。派法复用现有的 `reassign()`（换名额、续期、留痕），不另写一条派发路径。
4. **上限（需要你定，下面是建议值）**：
   - 每个 Agent 同时只拿 1 单（Agent 会话本来就是单线程）；
   - 每单最多 2 个施工候选、审查按现有 n；
   - 每个名额最多被分配器换人 2 次（与 `auto_reassign` 同一个计数），再不行就留给人；
   - 每周期最多派 5 单，防止一次把所有人都塞满后又同时超时；
   - 总开关 `priority.auto_allocate`，默认**只预演**：只把「本来会怎么派」写进页面和事件记录，不真派。
5. **界面**：概览加一张「调度」卡：三段积压各几单、每段能接的在线人数、分配器上一轮派了谁（或预演会派谁），一键从预演切到真派。

## 为什么先预演

画像里的原则：先最小实验、写清止损。分配器一旦派错（比如把施工派给不擅长的模型组），代价是一整轮返工；先看一周「它会怎么派」和你实际会怎么派是否一致，再开真派。

## 止损条件

真派一周内，被分配器派出的单 RETURN 率明显高于人派的（> 1.5 倍），或你手动改派超过 3 次 → 退回预演，调整「谁能接哪段」的规则。

## 放弃了什么

- 让普通 Agent 也处理 Leader 指令：指令要动决策、派发、合并，需要租约与 Leader 提示词，混进去会破坏「每条指令只被一位 Leader 领到」的保证。要更快就多接几位 Leader。
- 按模型能力打分自动选人：需要先攒「谁做什么类型的单通过率高」的数据（ADR 0008 正在攒档位数据），现在只按组分。
