# 0010 时间戳带时区偏移

- 状态：第 1 步已实施（fix/clock-skew）；第 2 步与第 3 步的后端口径已实施（任务 20261001-065052-5509）
- 日期：2026-10-01
- 起因：远端 Windows 的时区被自动改到美东（EDT，UTC-4），总线上的时间立刻错乱

## 背景（发生了什么）

总线的时间戳全是**不带时区的本地时间**（`bus_core.now_iso()` → `2026-10-01T12:32:14`），后端约 40 处用 `datetime.now()` / `fromisoformat` 计算时间差。

时区从 UTC+8 变成 UTC-4 后：

1. 旧心跳落到「12 小时后的未来」，`age = now - last_seen` 为负数，恒满足 `age <= 180`，**离线的 fable5-1-1 显示在线**（age=-38776s）。
2. Leader 租约判断同理：Leader 心跳在未来 → 租约永不过期 → 热备永远接不了班。
3. **同一时刻不同进程看到的「现在」不一样**：常驻进程启动时缓存了旧时区（Windows 上 Python 不会自动刷新），新起的进程用新时区。实测 controller 刚写入的心跳是 12:32，同一次查询报的当前时间是 00:32。

## 决定

时间戳一律写成**带偏移的 ISO 8601**（`2026-10-01T12:32:14+08:00`），读取时兼容旧的无偏移写法。每条时间戳自带偏移后，进程缓存的时区新旧、机器时区怎么变，比较结果都正确。

分三步，每步可单独回滚：

| 步骤 | 内容 | 状态 |
|---|---|---|
| 1 | `heartbeat_age()`：心跳超前 >300s 判不可信、按失联算并标 `clock_skew`；判在线 / 顶替提示统一走它。`lease_left()`：租约剩余时间超过 TTL+300s 判不可信、按过期处理（合法租约剩余不可能超过 TTL），`lease()` / `acquire_lease()` 据此放行热备；只看租约本身，有效租约不因持有者心跳异常被抢 | ✅ fix/clock-skew |
| 2 | `now_iso()` 改为带偏移；新增 `parse_ts()` / `age_sec()` / `now_dt()` / `iso_after()`；后端所有时间差与排序改为解析后比较 | ✅ 20261001-065052-5509 |
| 3 | 前端在线/离线与「多久没心跳」一律取后端的 `online` / `age_sec`（新增 `relAge()`）；`clock_skew` 在 Agent 卡片上出「时钟异常」标记 | ✅ 20261001-065052-5509 |

## 为什么不选别的

- **全部存 UTC（`Z` 结尾）**：同样能修好比较，但数据文件、日志和合并稿里的时间肉眼读起来要换算；带偏移既能正确比较，又保留本地可读性。
- **只加第 1 步的防护**：能挡住「离线显示在线」和「租约不过期」，但截止时间、TTL、排序等其他差值计算仍会在时区变化后错几个小时，不算根治。
- **要求机器固定时区**：是运维建议（已告知用户），但不能当作正确性的前提。

## 风险与回滚

- 第 2 步会让新旧两种写法在数据里共存一段时间，所以 `parse_ts()` 必须同时接受这两种写法。字符串比较、排序必须全部改成先解析再比较，评审时逐处检查。
- 回滚：第 1 步 `git revert` 本分支的代码提交（bc443d0 与租约修复）；第 2、3 步各自独立提交，可以单独 revert。旧写法始终可读，回滚不需要迁移数据。

## 进展 2026-10-01：截止时间改用 epoch（第二步的一部分）

实况：网页服务 / 各 Agent 的 MCP 进程启动时的时区不同（Windows 上 Python 进程沿用启动时时区），
派给 sota1/sota3 的评审在派发当秒就被判过期改名 `.json.expired`，Agent 永远领不到。

- 派发、requeue、reassign 写入 `deadline_ts`（epoch 秒），`deadline` 字符串保留给人看、兼容旧读者。
- `wait_task` / `mark_expired` / `close_stale` 统一走 `bus_core.deadline_passed()`：有 `deadline_ts` 只看它，旧任务退回字符串比较。
- 未做：心跳 `last_seen`、任务 id 排序、`created` 等其余本地时间字符串仍是第二步的剩余工作。

## 进展 2026-10-01：第 2、3 步落地（任务 20261001-065052-5509）

### 新的时间原语（`bus_core`）

| 函数 | 作用 |
|---|---|
| `now_dt()` | 当前时间，带本地偏移（aware）。所有差值计算的唯一起点 |
| `now_iso()` | `now_dt()` 的秒级 ISO 字符串，**带偏移**（`2026-10-01T12:32:14+08:00`） |
| `iso_after(sec)` | `now + sec` 的带偏移字符串（租约 `expires`、`deadline` 用） |
| `parse_ts(v)` | 解析成 aware datetime；解析不了返回 `None` |
| `age_sec(v, default=None)` | `now - v` 的秒数；解析不了返回 `default` |

### legacy（无偏移旧值）策略

`parse_ts` 接受三种写法：带偏移、末尾 `Z`、以及**无偏移的旧值**。旧值按**本机当前本地时区**补偏移。

这条是**有损**的，必须写明白：那串字符本来就没记录自己是哪个时区，机器时区改过之后旧值必然偏——
这正是本 ADR 要消灭的来源。legacy 分支只保证「不崩、按最可能的解释走」，不保证正确。
新写入一律带偏移，旧值会随心跳/租约刷新在一个 TTL 内自然换掉，不需要数据迁移。
测试里有一条用例专门把这个行为钉死，免得日后被误当成保证。

### 解析失败的方向（三处方向相反，都是有意的）

| 位置 | 解析失败时 | 为什么这样选 |
|---|---|---|
| `heartbeat_age()` | **按失联**（age=1e9，不标 skewed） | 反方向「按在线」会让一台时间戳坏掉的机器被当成活的一直派单，任务石沉大海、没有自愈路径；按失联最多多一次顶替 |
| `lease_left()` | **按过期**（0.0） | 坏处是租约可能被热备抢走、短时间出现双 Leader（抢锁是 `O_EXCL` 原子的，最终只有一个，epoch 也会 +1 可追溯）；反方向「按在线」会让一把坏租约永远锁死，热备永远接不了班，这个没有自愈路径 |
| `age_sec(at, 0.0)`（`console_wait` 顶替检查读 `handback.at`） | **按可接管**（age=0.0，立即交回租约） | 坏 `at` 把「刚交回」误算成「刚看过」→ 代理 Leader 立刻释放租约给真 Leader/其他热备；宁可多一次接管，也不能让坏时间戳把租约判成永远新鲜、阻塞交接。改动前该处解析失败曾按 9999 处理（不交回只删文件），方向已按上述原则修正并在此记录（qoder1 审查补记） |

两处的共同原则：**宁可多一次接管，不要一个永远卡住的状态**。

以及 `strftime("%Y-%m-%dT%H:%M:%S")` 写入——「只堵一半等于没堵」。

### skewed 的暴露

`status()` 增加 `clock_skew`（peer → last_seen/age_sec）与 `clock_skew_n`；Agent 卡片在 `clock_skew` 为真时出红色
「时钟异常」标记并给出 tooltip。不是掉线，是这台机器写下的时间戳不可信。

### 夏令时

EDT→EST 切换那一小时本地墙钟 `01:30` 出现两次。带偏移之后这是两个不同的瞬间（UTC 05:30 与 06:30），
差值算得对；无偏移写法在这一小时里**无法区分**，差值恒为 0。两条都有用例。
