# 0008 任务档位先自动记录，不加选择控件

**情况**：你的想法里有「matt 模式 / 快速模式」——有的事值得多个模型对读再合并，有的事一个模型直接做就够。ROADMAP 的做法是：先在派发时记一个「档位」，观察一个月你实际怎么选，再定默认规则。

**决定**：
- 网页派发（发起页、快速抽屉共用同一个提交点）和「重新派发」时，后端按实际派给几个 Agent 自动记 `tier`：1 个 = `fast`（快速单做），2 个及以上或全员在线 = `multi`（多模型对读）；同时记 `tier_source: "auto"`，将来加了手动选择就写 `"user"`，两类数据分得开。
- 任务详情顶部那行显示档位，悬停有说明。
- `python scripts/tier_stats.py [--days 30]` 出统计：真实记录、按人数推断的旧记录、连人数都没存的「未知」三类分开。

**为什么**：
- 你的实际选择已经体现在「勾了几个 Agent」上。再加一个眼下不改变任何行为的选择框，等于一个假控件，还多一步点击（画像：非创造性的事一键完成）。
- 推断放在后端，任何前端入口都覆盖到，也方便测试。

**审查修正（fable2 8bf5）**：「全员在线」在前端就展开成了具体名单，而这个工作台常年只有 1–3 个 Agent 在线——只有 1 人在线时，「全员对读」的意图会被记成 fast，和「我只要一个人做」无法区分，一个月后会把快速单做的比例顶高，还事后无法还原。所以派发时同时记 `online_n`（当时在线的 Agent 数，不含 Leader；查不到记 -1），统计时 `fast 且 online_n ≤ 1` 单列为「只有 1 人在线、无法区分」——它的含义是分不清，不是被迫，一个月后既不要算进快速，也不要整块当成本该对读。日期改为解析后比较。

**已知缺口**：Leader 从总线直接派的单（`bus_dispatch`，主要是审查单）不经过网页，暂不记档位；统计里这类旧记录落在「未知」。一个月后如果要把它们也算进来，可在 `bus_console post status=dispatched` 时从任务包取 peers 补记。

**一个月后怎么用**：看 `tier_stats` 里快速单做的比例。比例高 → 发起页默认只勾一个最合适的 Agent；比例低 → 维持现状。届时再决定要不要让档位改变流程（例如快速单做跳过合并稿）。

**回滚**：`git revert <本提交>`。已写进决策记录的 `tier` / `tier_source` 字段没有代码读取之外的副作用，留着无害。
