# 架构

> 适用版本：v0.4.0 起（2026-09-28）。更早的完整梳理与问题清单见 [reviews/ARCHITECTURE-REVIEW-20260928.md](reviews/ARCHITECTURE-REVIEW-20260928.md)。

## 一句话

**一个小而稳的核心（团队、派发、合并、拍板、施工），外面一圈可插拔的扩展（数据源、通知、页面），两者之间只有两条通道：HTTP 接口和事件记录。**

## 分层

└───────────────────────────┬────────────────────────────────┘

└──────┬──────────────────────────────┬──────────────────────┘

┌──────▼───────── 核心层 ─────────┐ ┌──▼──────── 扩展层 ─────────────┐

## 依赖规则（改代码时守住这几条）

1. **核心不认识扩展。** 核心模块不 import `bus_plugins` / `bus_intake` / `bus_feedback`，更不 import `plugins/` 里的代码。扩展可以调用核心的公开函数（如 `bus_projects.push_command`）。
2. **扩展之间不互相依赖。** 插件只认工作台的 HTTP 接口和 `events/`。
3. **接入层不写业务。** `bus_web.py` 的路由只做参数解析和转发；业务规则放进对应模块，才能单测。
4. **核心不知道其它项目在哪。** 需要个人助理的数据？由插件去读它已经导出的文件。需要让另一个项目知道任务完成了？它来读 `events/`。
5. **事件是旁路。** `bus_events.emit` 永不抛异常；写事件失败不能让派发、合并失败。

## 一个任务的一生

```
你点「派发任务」
  → POST /api/command {kind:"dispatch"}      bus_web → bus_projects.push_command → console/commands/
  → 事件 command.queued
Leader 的 bus_console(wait) 领到指令
  → bus_dispatch → inbox/<peer>/<task>.json  （Leader post status=dispatched 时 → 事件 decision.dispatched）
Agent 们 bus_wait_task 领题、bus_reply 交答案 → outbox/
Leader bus_collect → 写 log/<日期>/<task>.merge.md → post status=merged → 事件 decision.merged
你在「决策」里采纳
  → 需要落地的自动排 implement 指令 → Leader 用 bus_build 开施工：
    每个 Agent 一个 worktree（task/* 分支）→ 提交 → 另一个 Agent 审查（绑定提交号）
    → 临时副本 no-ff 合并 + 集成门禁 → main 快进 → post landed=true
  （本人采纳 / Leader post status=adopted 时 → 事件 decision.adopted）
```

注意：`decision.*` 事件只在有人调用 `post(status=…)` 时发出，取决于 Leader 是否 post 了状态。一定会自动发出的只有 `command.queued`、`intake.*`、`feedback.*`、`plugin.*`。

## 外部条目的一生

```
个人助理采集 → ~/.config/daily-assistant/data/collected/<日期>-<来源>.json
  → 插件 daily-assistant 发现文件修改时间变了（≤10 秒）
  → 过滤已完成、已见、未命中关键词的 → POST /api/intake        事件 intake.added
  → 你在「扩展与来源 → 收件箱」点「转成任务」                    事件 intake.accepted
  → push_command("external") → Leader 判断归属与做法
```

## 体验问题的一生

```
任意页面右下角「反馈」→ POST /api/feedback（自动附带页面、视图、最后点击的元素）
  → feedback/fb-xxxx.json，事件 feedback.created
  → 你在「体验反馈」点「转成任务」→ push_command("custom")：Leader 先复现、判断值不值得改
  → 值得改：按 WORKFLOW 开分支施工，合入后把反馈标为 done 并写提交号
  → 不值得：标 dismissed 并写理由
```

这就是「工作台自己迭代自己」的闭环：问题有记录、处理有去向、结果可追溯。

## 实时性

| 场景 | 机制 | 延迟 |
|---|---|---|
| 页面刷新 | `bus_web` 每秒比对数据目录签名，变了就推 SSE `change`，页面再拉 `/api/state` | ≈1 秒 |
| 外部数据源 → 收件箱 | 插件按修改时间轮询采集文件 | ≤ `poll_sec`（默认 10 秒） |
| 其它项目感知工作台 | 按游标读 `/api/event-log` 或直接读 `events/*.jsonl` | 取决于读方频率 |

为什么不用 WebSocket / 消息队列：单机、单用户、事件量每天几百条，文件 + SSE 足够，零依赖、可直接用文本编辑器排查。数量级变了再换（见 [ROADMAP](ROADMAP.md)）。

## 外部组件

- **ArenaX** 是**可选的外部闭源程序**，只服务「Arena 控制面」（账号池、会话池、模型路由、榜单）。工作台核心（总线、看板、施工、审查）不依赖它。
  - Arena 整体是可选插件 `plugins/arena/`（ADR 0014）：插件启用时由工作台插件管理器启动控制面，关掉插件 Arena 就不运行，工作台照常。
  - Arena 的业务 HTTP 调用都收口在 `plugins/arena/server/arena_upstream.py` 这一个接缝里。
  - ArenaX 不再由守护进程拉起：在 Arena 插件配置里填 `arenax_root`（本机目录，存在 `plugins.local.json`，不入库），插件就会顺带拉起并看护它；留空就不管。
  - 拿掉它时，Arena 页面显示「上游不可达」，其余照常。
  - 它依赖什么、工作台哪些地方用到它，见 [ARENA-DEPENDENCIES.md](ARENA-DEPENDENCIES.md)。
- **收件箱（`bus_intake`）和体验反馈（`bus_feedback`）是内置的扩展模块**，不是插件（见上方分层图的扩展层）。外部数据源以 `plugins/<id>/` 独立子进程的形式接入，只通过 HTTP 把条目送进收件箱，见 [PLUGINS.md](PLUGINS.md)。

## 借来的四条模式（外部实现的经验，不是外部的代码）

这四条来自对 `AgentWorkBench_Intake_0.1.0` 的只读评估（该包之后已删除）（合并稿 `log/2026-09-26/20260926-142500-537c.merge.md`）。处置结论是 **(c) 起步：不装、不搬码、不改现有代码**，所以下面写的是**模式**——它解决什么问题、我们现在缺在哪、落到我们体系里该长什么样。**本节没有一行代码来自那个包**，也不要把它当成"已实现"的描述；每条的"该长什么样"都是待办，不是现状。

放在这里而不是另开文件，是因为这四条讲的都是"一个任务/一次投递在我们体系里怎么流动"，与上面的〈一个任务的一生〉〈外部条目的一生〉〈实时性〉同属一层；单开文件会让读的人漏掉它们与现有流程的关系。

### 1. 事务性 Outbox + 租约

- **解决什么**："做了事"和"记下做了事"必须同生共死。若先发通知再记账，进程崩在中间就重复发；先记账再发，就可能记了没发。Outbox 的做法是：业务变更与"待发消息"写在**同一次原子写**里，另一个循环按租约把待发消息取走投递。
- **我们缺在哪**：目前只有一条**旁路事件记录**——`bus_events.emit` 独立追加 JSONL，出错返回 `{}` 不抛异常（[ADR 0003](adr/0003-events-outbox.md)），而且依赖规则明确规定事件写失败**不能阻断业务**。这**不是**事务性 outbox 的一半：业务状态变更与待发消息并不在同一次原子提交里，事件可能丢。所以缺两样：①业务变更与待发消息的原子记录（或可靠衔接）；②投递侧的领取租约——目前没有「某条通知已被某个消费者领走、N 秒内别人不要碰」的表达，多个消费者并行时只能靠各自的去重。
- **该长什么样**：待发条目落在事件记录之外的一份轻量队列里，每条带 `holder / lease_expires / attempt`；领取是"原子写 holder + 到期时间"，工作期间续约；**回收要同时看心跳、租约到期和宽限期，不能只看文件 mtime**。参考实现给的教训尤其重要：它的两条 UPDATE **确实带了 WHERE 守卫**（重复领取那一路被挡住了），真正的缺陷是**两处都不检查 `rowcount`** —— 某行在第一条 UPDATE 没抢到时仍被渲染进批量文本发了出去，**造成内容重复送达**，随后第二条 UPDATE 因租约不匹配静默失败、留下状态不一致。所以我们的规则是：**带守卫的写之后必须检查"到底改没改到"，没改到就把该条从本批里剔除，且不得静默吞掉**。

### 2. 授权绑方案哈希，且一次性消费

- **解决什么**：人点"同意"的那一刻，同意的是**当时那份具体方案**。若授权是一张不带内容指纹的通行证，方案在获批后被改动，旧授权仍然放行。
- **我们缺在哪**：我们已经有一处做对了——施工审查的 `PASS @<提交号>` 绑定确切提交，分支再动就要重审（[WORKFLOW 规则 5](WORKFLOW.md)）。缺的是**把同一口径推广到其它授权面**：安装/变更类操作、用户在工作台上点的"采纳/落地"确认，目前绑的是任务 id，不是方案内容。
- **该长什么样**：授权令牌 = `(动作, 方案内容的 sha256, 过期时间, 一次性标记)`。执行前重算哈希并比对，不一致就拒绝并要求重新授权；执行后立即作废该令牌（**一次性消费**，不能复用、不能重放）。审计里记下"批的是哪个哈希、执行的是哪个哈希"。

> **进展（2026-10-01，部分落实）**：派发确认落实了其中两点——**确认绑定具体内容**（项目 + 名单 + 问题 + 模式 + 上下文 + 时限的规范化签名，`web/v2/js/app.js` 的 `sendSignature`）与**一次性消费**（`submitDispatch` 入口即作废凭据；上传附件期间内容或草稿身份变了就中止，提交 038ee93）。它是**前端防误发的确认凭据**，不是 sha256 授权令牌：没有独立的授权过期时间（任务 `ttl_min` 不是授权过期），也没有「批的哈希 / 执行的哈希」审计。这些以及其它授权面仍是待办。

### 3. 结果不明时暂停，而非自动重试副作用

- **解决什么**：请求超时、连接中断、写到一半崩溃——这些是"**不知道成没成**"，不是"失败"。对带外部副作用的动作（发消息、下单、合并、装东西）自动重试，等于用一次不确定换两次副作用。
- **我们缺在哪**：目前多处失败路径是"重试若干次再报错"。对纯读、纯本地写没问题；对**有外部副作用**的动作没有区分"确定失败"和"结果不明"。
- **该长什么样**：给这类动作定义第三种终态 **`unknown`**（除 `ok` / `failed` 外）。落到 `unknown` 时：**停下、不重试**，把动作连同它的授权哈希、时间、能拿到的凭证（请求 id / HTTP 状态 / 对端回执）写进待核查队列，交人或交一次显式的核对流程判定。恢复只允许**一次有记录的受控重试**，不允许无限循环。

### 4. 增量回滚 ≠ 撤销现实副作用

- **解决什么**：回滚能把**我们自己的文件和状态**还原到之前的样子，但**发出去的消息、对外提交的请求、已经装到系统里的东西**不会因此消失。把两者混为一谈，会让"已回滚"被当成"什么都没发生"。
- **我们缺在哪**：我们在文档层面已经很谨慎（[ADR 0005](adr/0005-runtime-data-out-of-git.md) 明确写了 revert 与磁盘数据的冲突），但**没有一处明文区分"可回滚的状态"和"不可撤销的副作用"**。参考实现里那份安装收据就是反面教材：它的 `native_files_modified` 字段是**写死的空数组字面量**，而回滚准入条件恰好是判断该字段不为空——这条"安全检查"**恒真、没有证明力**（事实上它确实没改宿主文件，但这不是那个字段证明的）。
- **该长什么样**：任何变更动作的收据分两栏——**已回滚项**（我们改过、也确实还原了的文件/状态，逐条列路径与前后哈希）与**不可撤销项**（已发出的消息、已创建的外部对象、已装上的东西，逐条列时间与对端标识）。回滚完成后**必须把不可撤销项原样显示给人**，不得汇总成一句"已回滚"。收据里的任何字段，若不是由真实探测得出，就不许用作准入条件。

### 引用这四条时的限定（别写成更强的结论）

- 参考实现自带的 `MANIFEST.sha256.json` **只证明"包内自洽"，不证明来源可信**：清单与被校验文件同在一个压缩包内（53 条目对 54 文件，差额就是清单自身），**没有任何包外锚点**——无独立签名、无另行公布的清单哈希。
- 上一条提到的 `native_files_modified: []` 是写死的字面量，**不得拿它当防篡改凭据引用**。
- 它自报的"116 passed / 0 skipped"**尚未复跑**：核心声明零依赖，而某条渠道分支需要可选依赖，`0 skipped` 与之存在张力——要么测试环境装了可选依赖（那么"零依赖"只对核心成立），要么那些分支根本没执行。**在隔离环境复跑并逐项对账之前，不要把它当作已验证事实引用。**
