# AgentTeamWorkbench 工作流规范 v1

> 状态：草案，等本人确认后生效（2026-09-28）
> 适用对象：所有参与本仓库的人和 Agent，包括 Leader（controller）、施工 Agent、审查 Agent，以及本人手动修改。
> 一句话：**main 只接收"审过、测过、能快进"的分支；每件事一个分支、一个工作副本；每个结论都绑定到具体的提交编号。**

---

## 0. 先认识几个词（以后文档里都按这个意思用）

| 词 | 大白话 | 本项目里的样子 |
|---|---|---|
| 提交（commit） | 给代码拍的一张快照，有编号，比如 `e4b0735` | 每个提交只做一件事，说明写清楚"改了什么、为什么" |
| 主干（main） | 正在运行、大家都信任的那条线 | 8765 服务跑的就是 main；**任何人不直接往 main 提交** |
| 分支（branch） | 从某张快照另开的一条路，改坏了不影响主干 | `feat/…`、`fix/…`、`task/<任务号>/<Agent>` |
| 工作副本（worktree） | 把一个分支单独放进一个文件夹，几个分支能同时开工 | 统一放在 `.wt/<分支简名>/`；主目录只留给 main |
| 快进合并（ff-only） | main 期间没被别人改过时，直接把 main 的指针挪到分支末端 | 合完的 main 跟审过的提交**逐字节相同**，不会冒出没测过的"合并结果"（施工分支的例外见规则 6） |
| 审查绑定（pinned review） | 审查结论只对某个提交编号有效 | 审完又改了？编号变了，**原结论自动作废**，要重审 |
| 版本标签（tag） | 给 main 上某个提交起个好记的名字 | `v0.4.0`；每合一批就打一个，写进 CHANGELOG |

## 1. 七条硬规矩

1. **main 只读。** 人和 Agent 都不在主目录里改代码、不直接往 main 提交。连只改一个错别字的文档也要走分支（可以自审，见 §4）。
2. **一件事 = 一个分支 = 一个工作副本。** 不在别人的分支上顺手改别的事。
3. **一个提交只做一件事。** 修 bug、加功能、改格式分开提交，方便单独撤回。
4. **作者不审自己的代码。** 审查人和作者不能是同一个 Agent，也不能是同一个 Agent 的另一个窗口。（工具只校验名字不同：`bus_build_safety.set_review` 拒绝 reviewer=teammate，`pick_reviewers` 按 peer 名排除施工者本人，只从 `console/roles.json`（本机实例配置，不入库；缺失时自动回退到仓库模板 `tools/roles.json`）的 `reviewer_groups` 里挑人；"不是同一个 Agent 的另一个窗口"靠人工把关。）
   **同模型组互审**（例如 fable6 施工、fable2 审查）允许，但会优先避开：`pick_reviewers` 先挑与施工者不同模型组的在线审查者，没有才回退同组，此时任务包顶部会提示审查者换角度。开关是 `roles.json` 的 `policy.review_prefer_other_group`（默认开）。涉及安全、锁、合并流程的改动，尽量等别的模型组在线再审。
5. **审查结论绑定提交编号。** 结论第一行写 `PASS @<编号>` 或 `RETURN @<编号>`。之后分支上只要多一个提交，就要重审（至少审新增部分）。
6. **只用快进合并。** 合并前如果 main 已经前进了，先把分支变基或合并到新的 main、重跑测试、重新审查，再快进合入。不允许在 main 上解冲突。
   - **例外：`task/*` 施工分支**由 `bus_build merge` 合入——它在临时工作副本里用 `--no-ff` 生成合并提交、跑集成门禁，通过后再把 main 快进到这个合并提交。这个合并提交不另审。审查时工具会记下 main 当时的位置（`review_main`）；合并时如果 main 已经前进，结果和施工记录里会带上 `rereview` 提示：前进了几个提交、有没有碰本分支改过的文件。碰了（`risk: high`）就在界面施工状态上标「需重审」，由你或 Leader 决定是否补审；没碰（`risk: low`）只标「main 已前进」。工具只提示、不拦截，集成门禁照跑。
   - 人工分支（`fix/` `feat/` `chore/` `docs/`）严格按上面的快进规则。
   - **合并前必须先有对应 commit 的 PASS，人工分支不得绕过。** 施工分支（`task/*`）走 `bus_build merge` 时已有硬校验：`bus_build_safety.py` 的 `merge()` 在取锁后立刻判 `tm.get('review') != 'PASS' or tm.get('reviewed_commit') != commit` 并抛 `Merge requires PASS bound to the exact current submitted commit`（第 148–149 行），所以 PASS 必须绑定当前提交、改了就失效。**这道校验只覆盖走该入口的施工分支**：人工分支用 `git merge --ff-only` 直接合，工具管不到，只能靠这条规则。教训来自 `chore/tip-tails@7731571`——它先进了 main，PASS 是事后补的（复审 20260929-142841-b620 记录了这次顺序倒置）；结论虽是 PASS，但若当时是 RETURN，坏改动已经在主线上。
7. **运行数据不进代码。** 日志、收件箱、任务记录、锁文件、凭据、个人数据一律不提交（见 §6）。

## 2. 一次改动的完整流程

```
① 立项        决策已采纳（adopted），或本人明确下单
   │           → 记下：任务号、目标、验收标准
② 开分支      从最新 main 开：git worktree add -b <分支名> .wt/<简名> main
   │           → 在工作副本里干活，主目录不动
③ 施工        小步提交；每个提交都能说清"为什么"
   │           → 同时写 / 改测试
④ 自测        在工作副本里跑全部相关测试；贴命令和结果
   │           → 不稳定的测试按 §5 处理，不许改到变绿
⑤ 独立审查    把「分支名 + 提交编号 + 改动清单 + 验收标准」交给审查人
   │           → 审查人自己复跑，给出 PASS / RETURN @编号
   │           → RETURN：回到 ③，修完拿新编号重审
⑥ Leader 核验  Leader 在同一编号上复跑测试，确认审查结论对应这个编号
⑦ 合入        人工分支：git merge --ff-only <分支>（main 在主目录）
              施工分支（task/*）：bus_build merge（见规则 6 例外）
   │           → 重启 8765，冒烟检查（打开主要页面、派一条测试指令）
⑧ 收尾        写 CHANGELOG、打标签（批量时）、关闭相关决策记录
              → 删掉分支和工作副本
```

**谁做哪一步：**

| 步骤 | 负责人 |
|---|---|
| ① 立项 | 本人 / Leader |
| ②③④ 开分支、施工、自测 | 施工 Agent |
| ⑤ 独立审查 | 审查 Agent（不是作者） |
| ⑥⑦⑧ 核验、合入、收尾 | Leader |
| 验收拍板 | 本人：可以看 CHANGELOG 和冒烟结果，随时叫停 |

## 3. 命名

**分支名：**

| 前缀 | 用途 | 例子 |
|---|---|---|
| `feat/<主题>-<日期>` | 新功能 | `feat/plugin-manifest-20260930` |
| `fix/<主题>-<日期>` | 修 bug | `fix/zex-integration-20260928` |
| `chore/<主题>-<日期>` | 清理、配置、依赖 | `chore/untrack-runtime-data-20261001` |
| `docs/<主题>-<日期>` | 只改文档 | `docs/workflow-architecture-20260928` |
| `task/<任务号>/<Agent>` | 工作台施工模式自动建的分支 | `task/20260924-025949-3847/fable7` |

**工作副本目录：** `.wt/<分支名把 / 换成 ->`，主题里的修饰词可以省略。真实例子：`fix/zex-integration-20260928` → `.wt/fix-zex-20260928`；`feat/extensions-20260928` → `.wt/feat-extensions-20260928`。

**提交说明：** `类型(范围): 一句话说明`，正文写原因。类型用 `feat` / `fix` / `chore` / `docs` / `test` / `revert` / `refactor`。

```
fix(prefs): 补回 color/range 输入的 click 排除

9c53ead 解冲突时丢了这一行，导致取色器点一下就写入配置。
按 ef9ced7 原样补回；smoke_prefs_33fb 覆盖。
```

## 4. 什么情况可以简化

| 情况 | 可以省略 | 不能省略 |
|---|---|---|
| 只改文档、注释、错别字 | 独立审查（本人或 Leader 看一眼即可） | 分支、快进合并 |
| 紧急止血（服务起不来） | 先合后审：合入后 24 小时内补独立审查 | 分支、测试、事后在 CHANGELOG 标注"紧急" |
| 纯回滚（`git revert` 某个已合入提交） | 审查可以只看"回滚是否干净" | 分支、测试 |

**永远不能省略的：** 分支、测试、按规则 6 合并、运行数据不进代码。

## 5. 测试规则

- 每个功能分支至少新增或修改一个测试，证明改动生效；纯文档分支除外。
- **不稳定测试（flaky，时过时不过）：**
  - 在新旧两个版本上各跑 3 次，对比通过率。
  - 旧版本也不稳定：属于既有问题，登记到 `docs/FLAKY.md`，并开单修复。
  - 只在新版本不稳定：算本次改动引入，RETURN。
  - **禁止**为了变绿而删断言、加长等待、跳过测试，除非审查人明确同意并写明理由。
  - 浏览器测试由 `scripts/run_tests.py` 串行跑、失败自动复跑一次；只有 `docs/FLAKY.md` 里状态为「待查」的才允许「复跑通过」算过（输出打 ⚠），记录在 `log/flaky_runs.jsonl`。没登记的偶发照样是失败。
- Playwright 等浏览器测试必须用临时数据目录，不碰生产 console。
- **改了 `web/` 的分支，送审前跑一次界面体检**：`py -3 scripts/run_tests.py --audit`（或单跑 `py -3 scripts/ui_audit.py`）。它用真实浏览器打开各视图，列出对比度不达标、横向溢出、控制台报错；在 worktree 里跑审的就是本分支的前端。体检拦截一切写请求，所以可以对着正在用的服务跑。结果贴进送审说明。

## 6. 什么进代码仓，什么不进

参考个人助理 ADR-0008 的三层分离：

| 层 | 放什么 | 进 git？ |
|---|---|---|
| 代码层 | `*.py`、`web/`、`tests/`、`docs/`、配置**模板**、插件清单 | ✅ 公开仓 |
| 实例层 | 本机路径、端口、启用了哪些插件、项目列表 | ⚠️ 只进私有仓，或者不进 |
| 运行数据层 | `inbox/`、`outbox/`、`log/`、`peers/`、`console/`、`attachments/`、`projects/*/decisions.json`、锁文件、上传文件 | ❌ 不进 |
| 凭据层 | token、cookie、密钥 | ❌ 永远不进，也不出现在日志里 |

**施工模式的自动提交只能 `git add` 代码层目录**，不能 `git add -A`。

## 7. 版本与记录

- 采用 `v主版本.次版本.修订` 格式：
  - 破坏旧数据格式或旧接口：主版本 +1（1.0 之前记作次版本 +1）；
  - 加功能：次版本 +1；
  - 只修 bug：修订 +1。
- 每次合入 main，都要在 `CHANGELOG.md` 顶部追加一条：日期、版本、分支、提交编号、审查人、改了什么、怎么回滚。
- 每批合入后打标签：`git tag -a v0.4.0 -m "…"`。
- 回滚的标准做法是 `git revert <编号>`，走一个 `revert` 分支。**禁止** `reset --hard`、`push --force`、`rebase` 已合入的历史。

---

## 8. 定期清理（每周一次，Leader 执行）

- 已合入 main 的分支和工作副本：删除。
- 超过 14 天没动、也没合入的分支：
  - 列清单给本人，决定是继续、归档，还是删除；
  - 归档的做法是打 `archive/<分支>` 标签后删除分支，需要时还能找回。
- 核对 `.wt/` 目录，确保没有孤立的工作副本。
