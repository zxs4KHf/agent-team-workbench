## 以后

| 项 | 为什么不是现在 |
|---|---|
| 🕓 收件箱自动归类到项目（先建议、你确认） | 需要先攒一批"你实际怎么归类"的数据当样本；现在收件箱的"归属项目"下拉就是在收集这份数据 |
| 🟡 matt 模式 / 快速模式（任务分级：多模型对读 vs 单模型直做） | 先在派发时加一个"档位"字段记录，观察一个月你实际怎么选，再决定默认规则。2026-09-28 起网页派发自动记录（ADR 0008），2026-10-28 前后跑 `scripts/tier_stats.py` 看数 |
| 🕓 跨工作台门户（同一台机器上的多个工作台聚合到一处） | 需要各个工作台都先发 `events/`；届时做一个只读的聚合页（参考 Homepage 的做法），而不是合并代码 |
| 🕓 工作台之间标准字段（events-v1 推广到其它项目） | 本项目先跑稳一个版本，契约不再改了再推广 |
| 🕓 QQ / 微信 / 飞书消息实时扫描 | 飞书有正式接口可以做成数据源插件；QQ/微信没有官方接口，只能读本地导出，价值/风险比低，放到飞书之后 |
| 🕓 低风险条目自动执行（不经收件箱） | 需要收件箱先跑一段时间，统计出"你每次都点转任务"的那类条目，再只对那类开白名单 |
| 🕓 Arena 电脑操作 / 远程生图插件 | 插件接口已就绪，等有具体场景再做 |
| 🕓 使用数据分析、开源或商用方向 | 反馈与事件记录就是未来分析的原始数据；先攒数据，不先建分析系统 |

## 不做

| 项 | 理由 |
|---|---|
| ✋ 抽卡插件、指纹浏览器 | 与工作台目标无关 |
| ✋ 反向代理模型接口 | 违反服务条款，有封号风险 |
| ✋ 核心换框架 / 拆成微服务 | 单机单用户，模块化单体最合适；拆开的成本（版本错位、跨仓改动）远大于收益 |
| ✋ 插件之间互相依赖、插件改主界面代码 | 这是插件系统失控的典型原因（KDE 4、Eclipse、旧 Firefox 扩展） |
